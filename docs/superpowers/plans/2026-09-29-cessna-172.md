# Cessna 172SP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Second aircraft (C172) in Airframe and Fly modes behind an F-16A · C172 switch.

**Architecture:** Blender script → `public/cessna.glb` with the same part-extras contract as the F-16, so the explode viewer is reused; `flight.js` gets aircraft profiles; `fly.js` becomes aircraft-aware (profile, scale, prop/elevator effects); `main.js` routes `#<mode>/c172` and lazy-loads the second GLB.

**Spec:** `docs/superpowers/specs/2026-09-29-cessna-172-design.md`

## Global Constraints
- Part names: `fuselage wing struts propeller cowling windows door_L door_R interior main_gear nose_gear tail`; tail has child node `elevator`.
- Axis-aligned explode dirs, fuselage dist 0 (same rule as the F-16 check).
- C172 profile: cruise 32, throttle 44, turn 1.0, pitch rate 0.8, bank 45°; course scale 0.5, ring radius ×0.7; Fly model scale 0.73.
- Asset refs `?v=10`. `cessna.glb` lazy. Credit "FREE Cessna 172SP by NLM · CC BY 4.0".
- Don't push without asking (public Pages).

## Review Focus
1. Switching aircraft mid-explode → new aircraft starts assembled, toggle label matches.
2. Switching aircraft in Fly mid-race → race resets for that aircraft; best times don't cross.
3. `#airframe/c172` direct load and back button between aircraft.
4. C172 GLB load failure → error line, F-16 still usable.
5. Old links (`#airframe`, `#fly`, `#cockpit`, `#foo`) behave exactly as before.
